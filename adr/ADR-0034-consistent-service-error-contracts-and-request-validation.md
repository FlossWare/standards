# ADR-0034: Consistent Service Error Contracts and Request Validation

## Status
Proposed

## Date
2026-10-27

## Context

FlossWare exposes service contracts through repositories that may use different languages, frameworks, and runtimes. Even when business behavior is correct, contract drift can make clients unreliable: a shared HTTP dispatcher may return a status that a service schema does not declare; an error code may be missing from the documented vocabulary; request metadata may be validated differently by sibling services; and an implementation may silently discard meaningful input that the contract implies it processed.

These problems are cross-cutting engineering concerns. They belong in the generic FlossWare standards rather than being solved independently by each domain or runtime.

## Scope

This ADR applies to FlossWare-owned request/response service contracts, including REST endpoints and language-neutral schemas, and to the shared middleware, dispatchers, and validation code that implement them.

## Non-goals

- It does not require every service to expose identical business-specific error codes.
- It does not require every service to support every HTTP method or request metadata field.
- It does not prescribe one error-envelope format where an existing accepted contract standard already governs that format.
- It does not require identical status codes for genuinely different conditions.
- It does not authorize a breaking contract change without an explicit compatibility and migration decision.

## Decision

### Contract-to-runtime alignment

- A service contract SHALL document the HTTP statuses and machine-readable error codes that its endpoint can return, including applicable errors generated by shared middleware, dispatchers, authentication/authorization layers, and request parsing.
- For every documented error response, the HTTP status, error code, and response shape SHALL agree with the implementation and schema.
- Shared infrastructure errors SHALL be included in each affected endpoint's contract where they can occur. For example, 405 Method Not Allowed SHALL be documented for routes subject to method dispatch, and 408 Request Timeout SHALL be documented only where the request-processing path can actually produce that response.
- A service SHALL NOT declare a dispatcher status as impossible merely because its business handler does not generate it. Conversely, contracts SHALL NOT list statuses as supported without a plausible implementation path.
- Shared error codes MAY be represented through a common schema definition or reusable contract fragment. Services MAY add domain-specific codes while preserving the shared error vocabulary applicable to their runtime.

### Input validation and data preservation

- Implementations SHALL validate externally supplied values against the published contract before relying on them.
- If a service accepts a shared metadata field such as request_id, sibling implementations of that contract SHALL apply the same documented type, bounds, and invalid-input behavior. Optional fields MAY be omitted; if supplied, they SHALL be validated.
- An implementation SHALL NOT silently truncate, skip, or discard meaningful input when doing so could make the result appear successful but incomplete or misleading. It SHALL reject the request with a documented, appropriate error or explicitly document the transformation as part of the contract.
- Limits on request size, field length, collection size, and similar resources SHALL be explicit, consistently enforced, and reflected in the documented error behavior.
- Validation rules SHALL be proportionate to the field's semantics. This ADR does not require unrelated services to adopt the same arbitrary field limits; shared fields and shared contract families must agree on their limits.

### Contract validation in CI

- Repositories with machine-readable service schemas SHOULD validate representative success and error responses against those schemas.
- Contract validation SHOULD include a regression check that compares endpoint status declarations with the shared dispatcher/middleware policy, including method-not-allowed and timeout behavior where applicable.
- Contract tests SHOULD cover invalid metadata, boundary values, oversized inputs, and cases where the implementation must reject rather than silently lose meaningful data.
- A schema or runtime change that intentionally changes observable error behavior SHALL update the corresponding contract and tests in the same change.
- Cross-repository remediation MAY be incremental. Each repository SHALL track its own required implementation changes and preserve compatibility unless a separately approved breaking change is necessary.

## Consequences

### Positive

- Clients can rely on documented error responses across independently implemented services.
- Shared middleware behavior becomes visible at the contract boundary rather than appearing as undocumented surprises.
- Validation behavior is more consistent across languages and implementations.
- Regression tests can detect contract drift before release.
- Meaningful input is not mistaken for successfully processed input after silent loss.

### Negative

- Contract schemas and CI checks require maintenance when shared dispatcher behavior changes.
- Some existing schemas and runtimes will need coordinated updates.
- A common policy may reveal inconsistent legacy behavior that requires explicit migration rather than an immediate uniform change.

## Alternatives Considered

### Let each service document only errors generated by its business handler

Rejected. HTTP infrastructure and shared middleware are observable parts of the service contract.

### Require every service to use exactly the same error codes and status list

Rejected. Shared errors should be consistent, but service-specific capabilities and request paths legitimately differ.

### Allow implementations to silently drop input outside configured limits

Rejected. It can produce plausible but incorrect results and makes failures difficult for clients to detect.

### Rely on manual review without automated contract checks

Rejected as the sole safeguard. Review remains useful, but deterministic schema and dispatcher checks are repeatable and can prevent regressions.

The Tokenization contract review in FlossWare/claude-ensemble identified mismatches between shared dispatcher behavior and service schema declarations, inconsistent request metadata validation, and a path that silently discarded over-limit terms. The cross-service schema follow-up is tracked in [claude-ensemble issue #15](https://github.com/FlossWare/claude-ensemble/issues/15). This ADR defines the durable organization-wide policy; issue #15 tracks one concrete remediation batch.
