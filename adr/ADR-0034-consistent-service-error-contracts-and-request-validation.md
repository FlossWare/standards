# ADR-0034: Consistent Service Error Contracts and Request Validation

## Status
Proposed

## Date
2026-10-27

## Context

FlossWare exposes service contracts through repositories that may use different languages, frameworks, and runtimes. Even when business behavior is correct, contract drift can make clients unreliable: a shared HTTP dispatcher may return a status that a service schema does not declare; an error code may be missing from the documented vocabulary; request metadata may be validated differently by sibling services; and an implementation may silently discard meaningful input that the contract implies it processed.

These problems are cross-cutting engineering concerns. They belong in the generic FlossWare standards rather than being solved independently by each domain or runtime.

## Scope

This ADR applies to FlossWare-owned request/response service contracts, including REST endpoints and language-neutral schemas, and to the shared middleware, dispatchers, and validation code that implement them. HTTP-specific requirements apply to HTTP bindings. Other protocol bindings SHALL document equivalent failure categories, codes, and representations using the semantics of those protocols; they SHALL NOT be required to expose HTTP status codes in a protocol-neutral contract.

## Non-goals

- It does not require every service to expose identical business-specific error codes.
- It does not require every service to support every HTTP method or request metadata field.
- It does not select one universal error-envelope format. Envelope shape remains governed by applicable accepted contract standards; ADR-0031 is currently Proposed, and its recommendations do not become mandatory solely by reference. If ADR-0031 is accepted, its applicable guidance governs alongside this ADR.
- It does not require identical status codes for genuinely different conditions.
- It does not authorize a breaking contract change without an explicit compatibility and migration decision.
- It does not promise that every failure can carry a service-generated error envelope. Connection failures, TLS failures, and responses generated by upstream systems outside the service's control may not be serializable by the service.

## Decision

### Contract-to-runtime alignment

- For errors within the service's controlled response boundary, a service contract SHALL document applicable HTTP status, machine-readable error code, and representation/schema combinations that its endpoint can return, including errors generated by shared middleware, dispatchers, authentication/authorization layers, and request parsing.
- Contracts and tests SHOULD express valid combinations of status, error code, representation/schema, and retry semantics where retry behavior is meaningful. Independent status lists and code enums alone are insufficient if they permit invalid combinations.
- Known infrastructure-generated responses outside the service's controlled response boundary, and protocol-defined bodyless responses, SHALL be documented separately where relevant. A service SHALL NOT promise its own error envelope for failures it cannot serialize or for which the protocol does not permit that representation.
- Shared infrastructure errors SHALL be included in each affected endpoint's contract where the service can produce them. For example, 405 Method Not Allowed SHALL be documented for routes subject to method dispatch, and 408 Request Timeout SHALL be documented only where the request-processing path can actually produce that response.
- A service SHALL NOT declare a dispatcher status as impossible merely because its business handler does not generate it. Conversely, contracts SHALL NOT list statuses as supported without a plausible implementation path.
- Shared error codes MAY be represented through a common schema definition or reusable contract fragment. Services MAY add domain-specific codes while preserving the shared error vocabulary applicable to their runtime.
- For non-HTTP protocol bindings, contracts SHALL describe the equivalent protocol-specific failure categories, codes, and representations rather than imposing HTTP status codes where they do not apply.

### Input validation and data preservation

- Implementations SHALL validate externally supplied values against the published contract before relying on them.
- If a service accepts a shared metadata field such as `request_id` (an illustrative example, not a field defined by this ADR), sibling implementations of that contract SHALL apply the same documented type, bounds, and invalid-input behavior. Optional fields MAY be omitted; if supplied, they SHALL be validated.
- An implementation SHALL NOT silently truncate, skip, or discard meaningful input when doing so could make the result appear successful but incomplete or misleading. For example, dropping an over-length term from a token list while returning success is non-compliant; rejecting the request with a documented error, or applying an explicitly documented and observable transformation, is compliant.
- Limits on request size, field length, collection size, and similar resources SHALL be explicit, consistently enforced, and reflected in the documented error behavior.
- Validation rules SHOULD be proportionate to the field's semantics. Shared fields and shared contract families SHALL agree on their limits; unrelated services need not adopt identical arbitrary limits.

### Contract validation in CI

- Repositories with machine-readable service schemas SHOULD validate representative success and error responses against those schemas.
- Contract validation SHOULD include a regression check that compares endpoint status declarations with the shared dispatcher/middleware policy, including method-not-allowed and timeout behavior where applicable.
- Contract tests SHOULD cover valid status/code/representation combinations, invalid metadata, boundary values, oversized inputs, and cases where the implementation must reject rather than silently lose meaningful data.
- A schema or runtime change that intentionally changes observable error behavior SHALL update the corresponding contract and tests in the same change.
- Cross-repository remediation MAY be incremental. Each repository SHALL track its own required implementation changes and preserve compatibility unless a separately approved breaking change is necessary.

## Consequences

### Positive

- Clients can rely on documented error responses across independently implemented services.
- Shared middleware behavior becomes visible at the contract boundary rather than appearing as undocumented surprises.
- Validation behavior is more consistent across languages and implementations.
- Regression tests can detect contract drift before release.
- Meaningful input is not mistaken for successfully processed input after silent loss.
- Protocol-neutral contracts remain usable across different protocol bindings without conflating their failure semantics.

### Negative

- Contract schemas and CI checks require maintenance when shared dispatcher behavior changes.
- Some existing schemas and runtimes will need coordinated updates.
- A common policy may reveal inconsistent legacy behavior that requires explicit migration rather than an immediate uniform change.
- Testing valid error combinations may require more structured contract metadata than independent status and error-code inventories.

## Alternatives Considered

### Let each service document only errors generated by its business handler

Rejected. HTTP infrastructure and shared middleware are observable parts of the service contract when the service controls the response.

### Require every service to use exactly the same error codes and status list

Rejected. Shared errors should be consistent, but service-specific capabilities and request paths legitimately differ.

### Require every failure to use the service's error envelope

Rejected. Connection and TLS failures, upstream responses, and protocol-defined bodyless responses may be outside the service's control or unable to carry the expected representation.

### Allow implementations to silently drop input outside configured limits

Rejected. It can produce plausible but incorrect results and makes failures difficult for clients to detect. Explicit, contract-visible transformations remain possible where appropriate.

### Rely on manual review without automated contract checks

Rejected as the sole safeguard. Review remains useful, but deterministic schema and dispatcher checks are repeatable and can prevent regressions.

The Tokenization contract review in FlossWare/claude-ensemble identified mismatches between shared dispatcher behavior and service schema declarations, inconsistent request metadata validation, and a path that silently discarded over-limit terms. The cross-service schema follow-up is tracked in [claude-ensemble issue #15](https://github.com/FlossWare/claude-ensemble/issues/15). This ADR defines the durable organization-wide policy; issue #15 tracks one concrete remediation batch.
